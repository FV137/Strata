# Engine and source download verification

Setup pins the ready-made Windows engine to **v0.1.39**. It never falls back to
`releases/latest`. Linux normally compiles the engine locally, using the pinned
llama.cpp source archive. Model downloads and Python/CUDA/ROCm package installation
have their own existing behavior; this change does not add package signatures or
change model verification.

`engine-artifacts.json` is the trust anchor committed alongside `setup.py`. Every
engine or llama.cpp ZIP must match both its exact byte length and SHA-256 before
setup reads archive contents, extracts files, probes a downloaded HIP device tool,
or starts a setup-managed downloaded engine. `.done` files and versions in
`BUILD.json` are not integrity evidence.

addressed. No Windows engine executable was downloaded or run to establish these
pins, and no GPU execution was tested for this change.

## Cached archives and existing installations

Verified archives remain in `.cache/engine-artifacts/<sha256>/`. On every reuse,
setup re-hashes the archive, validates its entries, and compares every installed
file with the corresponding bytes inside it. The small `.artifact.json` file only
selects an archive and manifest entry; it does not authorize file hashes. Extra
engine files, modified DLLs or executables, symlinks, and modified metadata cause
verification to fail. HIP's copies of bundled runtime DLLs beside the executable
are checked against their original ZIP entries too.

Legacy downloaded engines without verifiable archives are reinstalled from the
pinned release. If verification or downloading fails, setup preserves their files
but refuses to execute them. A previously verified usable engine can still be
used offline. `BUILD.json` claiming a newer version cannot exempt an installation.
Deleting the archive cache requires setup to obtain the trusted archive again.

The extracted llama.cpp tree is compared with the verified archive before reuse.
An old or changed tree is replaced from verified source. The unused `tools/ui`
subtree is omitted to avoid Windows path-length issues. Extra Python bytecode files,
including `__pycache__/*.pyc`, require source re-extraction so cached code cannot override verified Python source. Locally compiled Strata engines and source
changes in this repository continue to use the existing build path. Local builds
are explicitly trusted local work, not authenticated release downloads. Both CUDA (`local`) and HIP
(`local-hip`) build metadata use this boundary. When switching from a downloaded, unknown or different-backend
installation to local compilation, all requested executables are built into a clean staging directory. Old
encoders, DLLs and other downloaded runtime files are never carried into the newly trusted local installation;
a failed compile preserves the prior directory and its prior trust status.

## Custom URLs and local release folders

An explicit `--prebuilt` override requires a trusted local JSON manifest supplied
with `--artifact-manifest`, or the `STRATA_ARTIFACT_MANIFEST` environment variable.
HTTP transport is refused; HTTPS URLs and local folders are supported. The
manifest is never downloaded automatically from the mirror. Obtain the digest from
a source you trust independently of the copy being checked. Hashing an untrusted
ZIP and approving that hash yourself does not establish who built it.

A mirror of the pinned official assets can use the committed manifest unchanged:

```sh
python setup.py --prebuilt https://mirror.example/strata/v0.1.39/ --artifact-manifest engine-artifacts.json
```

For a reviewed custom build, use the same JSON shape, with the actual archive
size, SHA-256, and expected compatible engine version:

```json
{
  "artifacts": {
    "strata-windows-x64.zip": {
      "version": "0.1.39",
      "size": 123629160,
      "sha256": "a862bcfa2330cd1c23f9b5d6e49f4027da8f8313842bd62e858ec6cd4533813a"
    }
  }
}
```

The values above describe the official asset, not a template digest for another
build. Keep the trusted manifest available on subsequent starts of a custom build.
Archive metadata must identify a release/prebuilt engine, compatible CUDA toolkit
or HIP backend and selected GPU architectures, safe relative library directories,
and all required executables. The custom manifest does not override the source
archive pin or the default official release's manifest.

## Extraction and failure behavior

Setup rejects absolute/traversing paths, Windows device names and alternate data
streams, ambiguous/case-duplicate paths, symlinks and other special entries,
encrypted entries, file/directory collisions, and excessive declared expansion.
Limits are 100,000 entries, 8 GiB total engine expansion, 4 GiB per engine file,
512 MiB source expansion, and 1 MiB for the engine metadata. Downloads cannot exceed
the manifest's exact size (itself capped at 1 GiB).

A complete archive is extracted to a fresh staging directory. Metadata and GPU
compatibility checks run before activation. Directory replacement preserves the
previous installation if activation fails, including a Windows sharing violation.
A leftover `engine.previous`, `engine-cuda12.previous`, or `llama.cpp.previous`
after a process interruption is preserved: inspect/restore or move it before
retrying setup. Setup does not treat a partial installation as a successful update.

This boundary covers setup-managed downloads, source extraction, starts,
calibration and HIP probing. It assumes the checkout, configured trust manifest,
and local compilation inputs are trusted. It does not defend against an attacker
who can replace `setup.py`, edit local-build metadata and inputs, race filesystem
changes during checks, or change system/PATH/pip libraries. Direct manual engine
or `serve/server.py` execution is outside these setup checks.

## Tests

```sh
python -m unittest tools.test_setup_engine_security tools.test_setup_pins.Engine tools.test_setup_amd.WindowsDetection
```

The tests use small synthetic ZIPs and mocked network responses. They exercise
hash and size mismatches, cached `.done` attacks, modified installed files,
attacker-controlled metadata, legacy offline starts, HIP probes/runtime copies,
unsafe ZIP entries and expansion, missing executables, incompatible builds,
activation rollback, cached-bytecode rejection through the actual Python import path, clean compilation
fallback and rollback, local HIP compatibility, and source-tree verification without downloading engines or
models.
